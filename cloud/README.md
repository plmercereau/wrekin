# Wrekin cloud

The relay between Claude and your machines: a Cloudflare Worker built with
TanStack Start (React, rendered on the server) and tRPC for the browser,
Better Auth on D1, one Durable Object per account that holds the node
WebSockets and routes commands, and the remote MCP server Claude talks to.

The wire contract with the Go agent is `../protocol/PROTOCOL.md`; its zod
schemas live in `src/protocol/`.

## Layout

```
src/server.ts           Worker entry (wrangler `main`): the machine surfaces first, then
                        TanStack Start; exports the AccountHub Durable Object class
src/http.ts             the machine surfaces: Better Auth (with the device/token form shim),
                        OAuth discovery, POST /api/nodes, POST /api/nodes/unregister,
                        GET /connect, POST /mcp (405 otherwise), JSON 404 under /api and /mcp
src/env.ts              bindings and secrets (src/cloudflare-env.d.ts types `env` of cloudflare:workers)
src/services.ts         auth + node store + hub, built from env (tests inject their own)
src/auth.ts             Better Auth: GitHub, Google, device authorization, MCP OAuth
src/crypto.ts           base64, Ed25519 verification, key fingerprints, random ids
src/db/                 Kysely types and the node store
src/hub/                core.ts (handshake, routing), account-hub.ts (the Durable
                        Object), client.ts (typed wrapper over the stub)
src/nodes/service.ts    register, list, remove, signed unregistration: the one implementation
                        behind the REST routes the Go agent speaks and the tRPC procedures
src/connect.ts          GET /connect: the nodes' WebSocket
src/mcp/                McpServer (@modelcontextprotocol/server v2), tools, session id
                        parsing, the /mcp handler behind requireMcpAuth
src/trpc/               context (env, services, session user), init, router:
                        nodes.list / remove / register / unregister, session.me
src/router.tsx          the TanStack Router with React Query and the tRPC provider
src/routes/             file routes: __root (layout, inline CSS, 404), index, login, device,
                        consent, nodes, api/trpc/$ (the tRPC server route)
src/routeTree.gen.ts    generated by the Start plugin on every build and dev run; committed
                        so `bun run typecheck` works before any build, as CI runs it
src/server/             server functions: the session and BASE_URL for every page, device
                        status, consent client, node list; worker.server.ts is the only
                        reader of cloudflare:workers
src/client/             the browser's Better Auth client and tRPC client
src/session-guard.ts    the login redirect of session-gated routes
src/styles.ts           the stylesheet; src/components.tsx the shared pieces
scripts/                the migration generator and the deploy-config renderer (Bun, outside the Worker)
migrations/             D1 migrations (0001 is generated, 0002 is the node table)
test/*.test.ts          run inside workerd only, against the built Worker (D1, Durable
                        Object, WebSockets, the server-rendered pages, tRPC over HTTP)
test/unit/*.test.ts     pure modules, run both inside workerd and in plain Node
test/shared/            suites shared by the two runs; test/helpers: fakes and harnesses
```

## Local development

```sh
bun install
cp .dev.vars.example .dev.vars     # then fill the OAuth client ids and secrets
bun run db:migrate:local           # applies migrations/ to the local D1
bun run dev                        # vite dev, with the Worker in workerd: http://localhost:8787
```

The OAuth apps must allow these callback URLs (with `BASE_URL` =
`http://localhost:8787` locally, `https://wrekin.platyplus.io` in
production):

- GitHub OAuth App: `<BASE_URL>/api/auth/callback/github`
- Google OAuth client: `<BASE_URL>/api/auth/callback/google`

An agent pairs against a local relay with
`wrekin auth --relay ws://localhost:8787/connect`.

## Tests and checks

```sh
bun run typecheck   # tsc --noEmit
bun run test        # vite build, then every test inside workerd against dist/server
bun run test:node   # test/unit only, in plain Node, for sandboxes that cannot bind a port
```

`bun run test` needs to listen on 127.0.0.1 (workerd); CI runs it. It builds
the Worker first because the workerd tests load `dist/server/wrangler.json`
and the bundle next to it: the pages are rendered by TanStack Start, which
only exists built. The pure modules (protocol schemas, the hub core, the node
service, the tRPC router with the memory auth and a fake hub, the MCP tools
through an MCP client, the machine surfaces of `src/http.ts`, the deploy-config
renderer) are also covered by `test:node`.

## Database schema

`migrations/0001_auth.sql` is generated from the Better Auth configuration:

```sh
bun run db:generate   # scripts/generate-auth-migration.ts
```

The script calls the schema generator Better Auth ships (`getMigrations`, the
one `@better-auth/cli generate` wraps) from the installed version of the
library, because the published CLI lags the library and omitted three unique
indexes. Re-generate whenever `src/auth.ts` changes its plugins, then review
the diff. `0002_nodes.sql` is hand-written.

Better Auth endpoints the agent uses: `POST /api/auth/device/code` (form or
JSON), `POST /api/auth/device/token` (JSON, or a form body that the Worker
re-encodes, RFC 8628 style). Sessions can be presented as
`Authorization: Bearer <session token>`.

## Deploy

Nothing in this directory deploys from a laptop or from GitHub Actions.
Cloudflare's Workers Builds is connected to this repository and deploys
`cloud/` on every push to `main`, the way Vercel builds from Git; the
platyplus/infrastructure stack (`sites/wrekin/tofu`) owns the D1 database,
the Worker entity and the name `wrekin.platyplus.io`, and its runbook
(`docs/runbooks/2026-11-wrekin-site.md` there) walks through the first
deploy.

`wrangler.jsonc` holds what belongs to the code: name, entry point,
compatibility date and flags, the bindings' names, the Durable Object
migrations. What belongs to a deployment is not in the repository:

| Value | Where it lives | How it reaches wrangler |
|---|---|---|
| The D1 database id | the stack (`d1_database_id` output) | build variable `WREKIN_D1_DATABASE_ID` |
| The public URL (`BASE_URL`) | the stack (`base_url` output) | build variable `WREKIN_BASE_URL` |
| The name `wrekin.platyplus.io` | the stack's custom domain | not in the config at all (`workers_dev: false`, no `routes`) |
| The five secrets | the Worker's *Variables and Secrets* in the dashboard | `wrangler deploy` never touches secrets |
| `MCP_ALLOWED_REDIRECT_HOSTS`, optional | the Worker's *Variables and Secrets* in the dashboard, as a secret so that a deploy keeps it | absent or empty: no restriction (the default) |

`MCP_ALLOWED_REDIRECT_HOSTS` is a comma-separated list of host suffixes,
`claude.ai, claude.com` for instance. When it is set, the MCP plugin's
`validateRedirectUri` accepts an authorization request only when its
`redirect_uri` is one the client registered *and* its host is one of the
suffixes or a subdomain of one, so no authorization code, and no token,
goes to another host; the consent page shows that host either way. Client
registration itself stays open (Claude's connector registers with Dynamic
Client Registration, and the plugin has no registration hook), so the list
is what bounds where a registered client can send the user. Unset or
empty, every registered URI is accepted, which is what the connector needs
out of the box; a native client calling back to `http://127.0.0.1:<port>`
needs `127.0.0.1` on the list.

Workers Builds settings: root directory `cloud`, build command `bun run
build`, deploy command `bun run deploy`, production branch `main`,
non-production branch builds off. `bun run build` first runs
`scripts/render-wrangler.ts`, which writes `wrangler.deploy.json` next to
`wrangler.jsonc` (same directory, so `main` and `migrations_dir` resolve the
same; the file is git-ignored) from `wrangler.jsonc` plus the two build
variables, and refuses to run without them; then `vite build` with
`CLOUDFLARE_VITE_WRANGLER_CONFIG_PATH=wrangler.deploy.json`, which the
Cloudflare Vite plugin reads, bundles the Worker into `dist/server/index.js`
and writes the configuration wrangler deploys, `dist/server/wrangler.json`
(the client assets in `dist/client/` are declared there by the plugin). `bun
run deploy` applies the migrations to the remote database with `-c
wrangler.deploy.json` and deploys with `-c dist/server/wrangler.json`. The
values of `BASE_URL` and `database_id` committed in `wrangler.jsonc` serve
local development only.

To rehearse the deploy configuration locally:

```sh
WREKIN_D1_DATABASE_ID=<uuid> WREKIN_BASE_URL=https://wrekin.platyplus.io bun run build
cat wrangler.deploy.json dist/server/wrangler.json
```

The MCP endpoint is `<BASE_URL>/mcp`, served by `@modelcontextprotocol/server`
v2 behind `requireMcpAuth` (POST only; the handler's `stateless` posture keeps
2025-era streamable HTTP clients working); nodes connect to
`wss://<host>/connect`.

## What the Worker stores about a node

Its id, account, name, public key, agent version, platform string and
created/last-seen timestamps. Never a private key, a token or any terminal
output; nothing in an MCP response is raw terminal output either.
